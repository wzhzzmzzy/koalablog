Reviewed the 99 open [Dependabot alerts](https://github.com/wzhzzmzzy/koalablog/security/dependabot) on `main@822e7efba55adfdc7fcd3bea4be4527cc0c8a67b`, including 5 critical, 33 high, 48 medium and 13 low alerts across 22 packages. GitHub counts separate manifest and lockfile alerts; npm audit also reports additional advisories and multiple installed versions, so its totals differ.

The changes cover 70 alerts with dependency updates. The other 29 have specific preconditions absent from the current application and are classified `not_used` below. This assessment uses the repository's Cloudflare configuration and source, not a production penetration test. Fixes take effect after the change is merged and the application is deployed.

## Validation

Environment: macOS ARM64, Node.js 22.18.0, pnpm 10.14.0. The install used the official npm registry and a fresh, project-local `node_modules` directory.

- Before updating: 631 unit/integration tests passed, with one existing skip.
- After updating and adapting error handling: 636 tests passed, with the same skip; all 36 D1 tests passed.
- A version-range check against the original 99 GitHub alerts found no affected installed versions or vulnerable direct manifest ranges for any of the 70 alerts classified for repair.
- `pnpm audit --registry=https://registry.npmjs.org --json`: raw findings fell from 130 to 22 (20 advisory records). The remaining findings are the scoped exceptions described above, including the Astro version-only AVIF advisory despite the patched Sharp dependency.
- Cloudflare build passed (25.11 s). Changed-file ESLint, generated-toolchain consistency and `git diff --check` passed.
- A final offline install with `--frozen-lockfile --ignore-scripts` passed without changing the lockfile.
- KaTeX MathML rendering and rejection of an inherited `trust` option passed a standalone smoke check using the same Markdown plugin/options as the application.
- `astro check` reports the same 22 errors in unchanged existing tests (`llms`, `rss`, `sync-attachment-auth`, `file-list`, `page-runtime`); changed files have no diagnostics.
- Complete browser regression: 107 of 108 cases passed in the initial run (10.8 min). The batch Svelte rebuild case timed out after a development-page reload reset its visible queue. The trace confirms the rebuild had already returned the expected `dependency_changed` response and a successful artifact attachment; the navigation completed after the test helper's 15-second reload window. Three consecutive isolated reruns passed (18.1/18.2/18.1 s) without changing application or test source. This is a remaining development-server timing flake, not a clean first-pass full-suite result.

The full suite exposed the Drizzle cause-wrapper incompatibility before the compatibility change. Focused tests also failed before the change for nested causes, misleading query parameters and an unrelated unique constraint, then passed with the updated classifier.

## Deployment boundary

Existing Deployed Svelte Render Artifacts embed their own runtime. Updating the application dependency upgrades the Dashboard and future builds; existing artifacts receive the new runtime only after an explicit rebuild and Deploy, as required by [ADR-0015](../adr/0015-require-explicit-svelte-artifact-deployment.md). This change does not rewrite persisted artifacts or deploy the application.
